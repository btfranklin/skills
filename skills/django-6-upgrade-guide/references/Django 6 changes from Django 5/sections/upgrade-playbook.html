Summary

Provides a step-by-step plan for upgrading a Django 5.x project to Django 6.0. Focuses on preparation (ensuring compatibility of Python, dependencies, etc.), identifying and fixing deprecation warnings, updating code for removed features, and testing before and after the upgrade. Includes a checklist mapping changes to the parts of the project they affect.

Guiding Questions

  • What steps should be taken to prepare a Django 5.x project for upgrading to Django 6.0 (in terms of environment and codebase)?
  • How can developers systematically find and fix issues (deprecated APIs, breaking changes) before and after the version bump?
  • What changes might be needed in tests, CI configurations, or project settings to accommodate Django 6.0’s differences?

Insights

Prepare environment and dependencies

Evidence
It’s important to ensure that all project dependencies and the runtime environment are ready for Django 6.0. The official advice is to upgrade Django-related libraries to their latest versions, as older versions may not support Django 6.0 yet (docs.djangoproject.com). In practice, this means checking that major packages (Django REST Framework, Celery, etc.) have Django 6.0 compatibility releases. If some dependencies lag behind, consider waiting or finding alternatives, because using them with Django 6.0 could break the project.
Implications
Before attempting the upgrade, teams should update their Python environment to meet Django 6.0’s requirements (e.g., Python 3.12+). All third-party apps in INSTALLEDAPPS should be reviewed: are they officially supporting 6.0? It's wise to proactively bump those packages to versions that advertise support for Django 6.0. If a crucial dependency hasn’t been updated for Django 6.0, the upgrade might need to be postponed or that dependency replaced, since incompatibilities could cause runtime errors.

Resolve deprecation warnings early

Evidence
A key practice is to run the project’s test suite under Django 5.2 with deprecation warnings enabled (using -Wa or PYTHONWARNINGS). Django’s upgrade guide suggests fixing all deprecation warnings in advance (docs.djangoproject.com) (docs.djangoproject.com). For example, running tests with: bash python -Wa manage.py test will surface any usage of features that Django 6.0 removed or changed. By cleaning these up in the 5.x codebase (for instance, replacing deprecated settings or function calls with their recommended alternatives), you can drastically reduce surprises when switching to 6.0.
Implications
Deprecation warnings are essentially Django’s “heads-up” for things that need to be changed. Addressing them in advance means that by the time you upgrade to 6.0, your code is already using supported APIs. This step catches issues like soon-to-be-removed methods (ensuring you’ve switched away from them) and transitional settings that should be updated. In CI pipelines, you might even elevate warnings to errors during tests to enforce that no new deprecated usage is introduced in the meantime.

Incremental upgrade and testing

Evidence
If your project is not already on the latest 5.x release, upgrade to the latest patch (5.2.x) first and run all tests on it. Django’s guidance is to perform upgrades one release at a time (e.g., from 5.1 to 5.2, then to 6.0) rather than jumping multiple versions (docs.djangoproject.com). Once your codebase is on 5.2 and free of deprecation warnings, pin your Django dependency to 6.0 and run the full test suite and QA checks again. Expect to see failures where behavior changed (for example, if tests asserted exact outputs that have subtly changed in 6.0).
Implications
An incremental approach minimizes the scope of change at each step, making it easier to pinpoint issues. Upgrading to Django 6.0 directly from an earlier version without intermediate steps can compound problems and make debugging difficult. By doing a staged upgrade (and using the latest patch releases for each interim version), you isolate changes and maintain stability. After upgrading, thorough testing (unit, integration, and manual testing of critical user flows) is essential to catch any differences in behavior introduced by Django 6.0.

Update code for breaking changes and adjust tests

Evidence
Some test failures after the upgrade can reveal places where Django 6.0 changed behavior. For example, the JSON serialization output now includes a newline at the end, which may break tests that compare exact strings (docs.djangoproject.com). Developers should update such tests (or the code if needed) to accommodate the new behavior. Additionally, ensure that settings like DEFAULT_AUTO_FIELD are explicitly set if needed (to avoid unexpected migration diffs), and that any custom ModelAdmin or form classes conform to the new APIs (e.g., adding the request parameter). Running python manage.py check and looking for any system check errors is also useful after upgrading.
Implications
This step is about ironing out the last quirks. Many changes (like the newline in JSON, or the staticfiles manifest ordering) don’t affect application logic but do affect reproducibility and tests. It’s important to review failing test assertions and logs for subtle changes and update them. Also, where Django 6.0 has new defaults (such as stricter email header handling or changed message icon styling in admin), the team should decide if any configuration tweaks or documentation updates are needed for users. By the end of this checklist, the application should run on Django 6.0 with all tests passing and no warnings, meaning it’s ready for production rollout.
