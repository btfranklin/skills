Summary

Details the features and behaviors removed or altered in Django 6.0 that may break 5.x applications. Highlights settings that have new default values, removed APIs (with their replacements or workarounds), and how to identify code impacted by these changes.

Insights

Primary key field default changes to BigAutoField

Evidence
In Django 6.0, the DEFAULT_AUTO_FIELD setting now defaults to django.db.models.BigAutoField (previously it defaulted to AutoField) (docs.djangoproject.com). Most projects were already prompted to set this explicitly since Django 3.2 (via system check W042), but if a project never did so, it will now see new migrations using BigAutoField for primary keys. The official guidance is that such projects should explicitly set DEFAULT_AUTO_FIELD = 'django.db.models.AutoField' in settings (or default_auto_field in an app’s AppConfig) if they wish to preserve the old behavior (docs.djangoproject.com).
Implications
For projects upgraded from Django 5.x without having addressed the default auto field warning, the change in default means migrations for new models (or apps) could generate big integer primary keys by default. Teams should either accept BigAutoField going forward (preferred for scalability) or pin the setting to AutoField to maintain consistency with existing schema. It’s important to apply the setting or run the necessary migrations before deployment to avoid runtime schema inconsistencies.

Removal of legacy API patterns

Evidence
Django 6.0 removes several previously deprecated behaviors. For example, methods now enforce keyword-only arguments where positional usage was allowed in the past: ModelAdmin.lookup_allowed() must include the request parameter, and functions like format_html() no longer accept being called without arguments (docs.djangoproject.com). Likewise, support for calling model methods with positional arguments has been dropped – e.g. passing positional force_insert/force_update flags to Model.save() (or Model.asave()) is no longer supported (docs.djangoproject.com).
Implications
Code that relied on the old calling conventions will raise errors in Django 6.0. Developers should update any ModelAdmin.lookup_allowed overrides to include a request parameter in the signature, and revise calls to utility functions like format_html to use keyword arguments or remove them if they were used as no-op wrappers. Model save calls should be audited to ensure that force_insert or force_update are passed as named parameters. These changes were all preceded by deprecation warnings in Django 5.x, so any runtime warnings should be treated as indicators of code that must be updated.

Email system refactored to modern API

Evidence
Django’s email sending classes now use Python’s standard email.message.EmailMessage internally, replacing older mechanisms. As a result, some undocumented hooks have been removed: for instance, the mixed_subtype and alternative_subtype properties on EmailMessage/EmailMultiAlternatives are no longer supported, and the encoding property no longer accepts legacy email.charset.Charset objects (docs.djangoproject.com). Because the internal implementation changed significantly, any custom email subclasses that override internal methods may need to be reviewed for compatibility (docs.djangoproject.com).
Implications
Most applications that use Django’s email API in the standard way (via send_mail, EmailMessage.send(), etc.) should not need changes, but those with custom email processing or subclasses could be affected. Projects should test any custom email sending logic to ensure that the formatting and attachments still work as expected. Notably, the email message structure is now handled by Python’s library, which improves Unicode handling, but any code peeking into the internals of email message objects will need adjustment.

Deprecated features from 5.x now removed

Evidence
Django 6.0 completes the deprecation cycle for features flagged in Django 5.0 and 5.1. For instance, the transitional form renderers (DjangoDivFormRenderer and Jinja2DivFormRenderer) have been removed, BaseDatabaseOperations.field_cast_sql() is removed, and support for the old Oracle driver (cx_Oracle) is dropped (docs.djangoproject.com). Additionally, any use of the now-removed prefetching APIs (Prefetch.get_current_queryset(), custom get_prefetch_queryset() methods, etc.) or the get_cache_name() field cache helper will no longer work in 6.0 (docs.djangoproject.com) (docs.djangoproject.com).
Implications
These removals primarily affect less common or more advanced use cases, but they can be critical if your project or its dependencies rely on them. For example, projects using an Oracle database must install the newer oracle client library (python-oracledb) since cx_Oracle is no longer supported. Similarly, any custom model prefetch logic should be refactored to use the standard Prefetch API patterns provided by Django. Teams should review the Django 5.0 and 5.1 deprecation notes to ensure that none of those now-removed features are still in use in their codebase.
