- **Built-in dialog and popover elements cover common layered UI needs**
  - Evidence: Native HTML now includes elements specifically made for layered interfaces that used to require custom code. For example, the `<dialog>` element provides a modal dialog box behavior (with a browser-managed backdrop and focus trapping), and the new global `popover` attribute allows any element to act as a popup overlay ([web.dev](https://web.dev/articles/baseline-in-action-dialog-popover#:~:text=The%20%60,list%20without%20being%20logged%20in)). These built-ins encapsulate functionality like light-dismiss (clicking outside to close) and proper stacking of content, which previously developers had to implement themselves. As of 2025, both `<dialog>` and popovers are considered baseline features in modern browsers, meaning developers can use them in production knowing that support is consistent across major browsers ([web.dev](https://web.dev/articles/baseline-in-action-dialog-popover#:~:text=Most%20of%20these%20user%20interface,library%20you%20choose%20gets%20right)).
  - Implications: By using `<dialog>` for modals or `popover` for tooltips/menus, developers reduce the amount of custom JS needed and get accessible behavior by default. It’s still important to test these components (for example, ensure dialogs have appropriate focus when opened and a descriptive title), but the heavy lifting (like preventing background interaction while a modal is open) is handled by the browser.

When a modal dialog opens via `showModal()`, the rest of the page becomes inert (non-interactive) without extra coding ([web.dev](https://web.dev/articles/inert#:~:text=Source)). **Insights**
- **Many components can be purely declarative or use one-liner scripts**
  - Evidence: Common UI widgets that once demanded a JS library can often be created with native elements and a sprinkling of script for glue. For example, to open a modal dialog, a developer can simply call `dialog.showModal()` in response to a button click, and the browser will handle displaying the dialog and focusing it ([web.dev](https://web.dev/articles/baseline-in-action-dialog-popover#:~:text=Use%20the%20,dialog)). Similarly, for popovers like tooltips or dropdown menus, adding a `popovertarget` attribute to a button and a corresponding `popover` attribute to a content element ties them together — clicking the button toggles the popover without custom JS logic ([developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using#:~:text=least%20one%20control%20button%20,of%20the%20popover%20to%20control)). Tabs and accordions can be made using `<details>` or radio input hacks in CSS. These approaches mean that the interactive behavior is either handled entirely by the browser or requires just a couple of lines of code, rather than a full component class.
  - Implications: Having the browser manage component behavior leads to less buggy interactions because standard events (like Escape to close a dialog or clicking outside to dismiss a popover) are already implemented. Developers should lean on these patterns for simplicity. The small scripts that tie things together (e.g., adding an event listener to call showModal()) are straightforward and don’t carry the maintenance burden of large framework components. This also makes an app more understandable: other developers can see an HTML button and dialog and know what’s going on, as opposed to deciphering a complex framework-specific component.

  - Evidence: Thanks to advancements in CSS, many interactive effects can be achieved with no JavaScript at all. Developers have demonstrated patterns like CSS-only accordions (using the `<details>` element or a checkbox + label trick), carousel sliders using the `:target` pseudo-class or animation keyframes, and even modest modals via the `<dialog>` element’s `[open]` attribute toggling. A report in 2024 noted that features such as CSS scroll snapping, new selectors (like :has()), and better form controls have "dwindled" the need for JS for layout and simple interactions ([nicklewis.dev](https://nicklewis.dev/how-much-do-we-need-javascript-in-2024/#:~:text=With%20new%20features%20launched%20in,layout%20and%20interaction%20is%20dwindling)). As examples, you can create a responsive image gallery that uses the `:target` selector to open fullscreen images, or use media queries and the `inert` attribute to simulate modal focus control in a no-JS environment. These techniques underscore that not every interactive experience mandates a scripting solution.
  - Implications: Using CSS for interactivity where possible can drastically cut down on complexity and payload. It also tends to be very fast, since toggling a CSS state (like a class or a `:checked` state) avoids JavaScript execution entirely. The downside is that purely CSS solutions can sometimes be less flexible (logic flows are harder to manage), so they work best for relatively simple toggling states or visual effects. Developers need to weigh when a CSS-only pattern is sufficient and when the interactivity is complex enough to warrant adding a bit of JavaScript.

This approach keeps state visible in the DOM, making it easier to debug and resilient to partial rendering updates. Tools such as Hotwire’s Turbo or Alpine.js allow developers to continue writing primarily HTML (with attributes for behavior) and avoid a full re-architecture. The trade-off is that using several small tools requires discipline to keep things organized, and developers must ensure these enhancements are layered cleanly (so that if the JS fails, a server round-trip or a full page reload still handles the action). Proper documentation of these patterns within the team is important so that everyone knows the conventions (for example, using data-attributes for certain states or events).

### Server-Driven UI and Partial Updates (server-driven)
Discusses strategies for keeping the server as the source of truth for the application's state and UI, while still delivering a smooth, app-like experience. This includes traditional multi-page navigation patterns (links and forms) enhanced with modern techniques like the View Transitions API for seamless page changes, incremental server rendering (streaming updates), and the use of ultra-light JavaScript libraries to update parts of the page without a full reload. It underscores how to achieve dynamic functionality (like optimistic UI or modal flows) in a server-centric model.

**Key Terms**
- Multi-page application (MPA)
- Partial page update
- Post/Redirect/Get (PRG)
- View Transitions API
- Streaming SSR
- HTMX/Turbo (HTML over the wire)

**Guiding Questions**
- How can we implement an app-like user experience (transitions, quick updates) while keeping rendering and state management on the server side?
- What patterns enable updating only parts of a page (instead of a full reload) without using a client-heavy framework?
- How do newer browser APIs like the View Transitions API facilitate smoother navigation in a server-driven context, and what are the limitations?

**Insights**
- **Progressive enhancement of navigation using View Transitions**
  - Evidence: In a server-driven app, clicking a link traditionally triggers a full page reload. Today, the View Transitions API allows browsers to capture the outgoing and incoming DOM and animate between them, even for a full document navigation. This means multi-page apps can have smooth cross-fade or slide transitions akin to an SPA. As of Chrome 126, cross-document view transitions (for same-origin navigations) are supported and can be enabled with a simple CSS directive, without any heavy scripting ([developer.chrome.com](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document#:~:text=cross,the%20user%20of%20your%20website)). When used, the user still triggers a normal navigation (preserving the simplicity and reliability of page loads), but the experience is enhanced with a visual continuity. Other browsers are expected to follow, given this is a standards-track feature. This approach marries the robustness of server-side navigation with the polished feel of client-side transitions.
  - Implications: By adopting the View Transitions API (progressively, with a fallback to normal page loads if unavailable), developers can avoid complex custom animation code for page changes. It helps HTML-first apps achieve that "smooth" feeling often associated with SPAs, which can improve perceived performance and user delight. Teams should be mindful that this is a progressive enhancement: the app should not depend on the transition to function. Also, there might be some tweaking needed (like ensuring stable element identifiers between pages) to get the best effect. Overall, this API lowers one of the perceived gaps between MPAs and SPAs.
  - Citations: 9, 18
- **Partial page updates keep the experience dynamic without a full SPA**
  - Evidence: Server-driven UIs can still update small parts of the interface quickly by sending HTML fragments instead of requiring a full reload. Techniques like AJAX (fetching HTML snippets) or WebSocket updates have long existed, but modern solutions have streamlined this. For instance, Hotwire’s Turbo Drive and Turbo Streams enable developers to perform partial page updates by simply returning HTML from the server; the client-side Turbo library then morphs the DOM accordingly ([hotwired.dev](https://hotwired.dev/#:~:text=Turbo%20Image)). Another example is HTMX, which allows using attributes like `hx-get` on elements to declaratively fetch and swap in HTML from the server in response to events. These tools adhere to the HTML-first principle by keeping templates and rendering on the server (you send updated HTML for a list, a table, etc.), yet the user experience is seamless and fast like an SPA for those interactions. Importantly, because the server is still crafting the HTML, there’s a single source of truth and no complex client-side state to synchronize.
  - Implications: Partial updates can greatly improve perceived performance and interactivity in a multi-page app. Users can, for example, submit a form and see just a list update or a new table row appear without a full refresh. For developers, this means they can often reuse server-side templates for these snippets. They must ensure idempotence and consider how to manage history (e.g., if the URL should change or not for these actions). There is also a slight complexity in adding such a library to a project, but libraries like Turbo are lightweight compared to full frameworks and come with sensible defaults. The benefit is retaining server logic and avoiding data duplication on client and server. If JavaScript is disabled or fails, the app still works (it will just do a normal page reload), which speaks to the robustness of this approach.
  - Citations: 2
- **Server-first design simplifies state management and improves resilience**
  - Evidence: In an HTML-first paradigm, the server maintains the authoritative state, and each interaction (like clicking a button or submitting a form) either navigates to a new URL or returns a fresh HTML snippet reflecting the updated state. This post-redirect-get pattern and form-first workflow inherently prevent many common issues like client-side state becoming out-of-sync with server data. It also improves security and SEO since every piece of content is rendered on the server (there's less risk of missing metadata or exposing insecure APIs directly to the client). Moreover, real-world analyses have found that sites built with progressive enhancement (server-rendered pages augmented with minimal JS) often load significantly faster on mobile devices than heavy SPA sites ([johal.in](https://johal.in/progressive-enhancement-in-htmx-dynamic-uis-with-minimal-javascript-and-python-backends/#:~:text=JavaScript%20frameworks%2C%20developers%20are%20rediscovering,integrations%20where%20every%20millisecond%20counts)). They also tend to handle unexpected conditions gracefully: if a script doesn’t load or a network hiccup occurs, the user still has a functional page, because the core interactions are anchored in standard links and forms. Maintaining this kind of resilience is a key quality goal for many teams adopting the approach.
  - Implications: The emphasis on server-driven interactions means developers need to design robust back-end endpoints for every action (which is good for API design and reuse). Testing efforts might shift more toward integration tests that ensure the rendered HTML is correct for various scenarios, rather than unit tests of client-side logic. While performance can greatly improve (smaller bundles, less JS execution), teams should monitor server load and scalability, since more work is done on the server per interaction. Caching strategies (HTTP caching, server-side caching) become crucial to ensure the server-first approach remains snappy under load. Finally, while an HTML-first app is more resilient by default, teams should still implement thorough accessibility and user testing to catch any gaps in the enhanced vs. non-enhanced experience.
  - Citations: 11

**Guiding Questions**
- Does using native HTML features improve accessibility, and what pitfalls should developers still watch out for?
- How does the performance of an HTML-first app compare to a typical framework app, and how can teams measure and ensure a fast user experience?
- What are the maintainability implications of minimizing frameworks (for example, in terms of developer productivity, code organization, and long-term scaling)?

**Insights**
- **Semantic HTML first: the foundation of accessibility**
  - Evidence: A key rule in accessibility is to use native HTML elements whenever possible, because they come with predefined semantics and browser support. By adhering to an HTML-first approach, developers naturally follow this rule. For instance, using a real `<button>` element (instead of a `div` with a click handler) means keyboard and screen-reader support is handled automatically. The same goes for using `<label>` with form inputs, or `<nav>` and `<main>` landmarks for structure. The benefit is less reliance on ARIA roles to patch up custom controls. In fact, many ARIA attributes that developers used in the past to fix custom widgets are no longer needed when using the right elements ([www.sitelint.com](https://www.sitelint.com/blog/native-built-in-browser-elements-you-can-use-today-instead-of-aria-or-role-attributes#:~:text=But%20today%2C%20many%20of%20those,better%20results%20and%20fewer%20bugs)). That said, developers still need to test edge cases – e.g., ensuring custom elements provide necessary ARIA labels or that focus order remains logical when HTML is manipulated – because without a framework, there's no abstraction hiding those details. Overall, though, staying semantic makes achieving accessibility much easier and more robust.
  - Implications: When building without a framework, developers must take direct responsibility for accessibility – there's no built-in linting or community plugin doing it for you. This means incorporating accessibility testing into the workflow (using tools like screen readers, automated checkers, and referencing the WAI-ARIA Authoring Practices for any custom patterns). On the upside, simpler, semantic HTML outputs often mean fewer things can go wrong. There’s typically less dynamic content to confuse assistive tech, and more predictable interactions. Teams should create an accessibility checklist specific to their components, especially if they built custom ones (e.g., ensure every interactive element is focusable and labeled). Embracing HTML-first often aligns perfectly with accessibility best practices, which recommend using native controls as much as possible.
  - Citations: 12
- **Performance wins: less JavaScript means faster load and execution**
  - Evidence: One of the strongest arguments for HTML-first UIs is the performance improvement. By shipping mostly HTML and minimal JS, the amount of JavaScript the browser must download, parse, and execute is dramatically reduced compared to a typical SPA. This often results in faster First Contentful Paint and Time to Interactive. Case studies have observed substantial gains: for example, sites built with progressive enhancement techniques (server-rendered HTML augmented with a bit of JS) can load up to 70% faster on mobile networks than their SPA counterparts ([johal.in](https://johal.in/progressive-enhancement-in-htmx-dynamic-uis-with-minimal-javascript-and-python-backends/#:~:text=JavaScript%20frameworks%2C%20developers%20are%20rediscovering,integrations%20where%20every%20millisecond%20counts)). Smaller JS bundles also mean less CPU work on the client, benefitting users on low-power devices. Additionally, server-side rendering allows content to be visible and indexable immediately, which can indirectly help SEO and perceived speed (since users see content without waiting for a large JS app to hydrate). Tools like Lighthouse and Core Web Vitals metrics often show improvements in Largest Contentful Paint (LCP) and Cumulative Layout Shift (CLS) when the bulk of UI is delivered as static HTML/CSS rather than built via client-side JS.
  - Implications: Teams adopting this approach should set performance budgets (e.g., JS bundle size limits) to guard against creeping back to heavy client-side code. They get the advantage that improving server response times directly improves the UX (since the server is doing the rendering). However, they should also invest in good back-end performance practices (caching, queries optimization) because the server workload is higher. To measure success, they can track Core Web Vitals and compare them against industry benchmarks or the previous framework-based implementation. They may also find that less time is needed debugging performance issues like long script tasks or memory leaks on the client. In summary, an HTML-first approach aligns well with performance budgets by design, but it shifts some responsibility to the back-end performance.
  - Citations: 11
- **Maintainability relies on strong conventions instead of framework rules**
  - Evidence: Without a framework’s structure and tooling, maintainability of a large project depends on the team establishing solid conventions. This includes how to organize templates and partials on the server, how to write modular CSS (perhaps using BEM or modern CSS scoping features), and how to structure any JavaScript enhancements in a clear way. Some teams adopt a design system approach with Web Components or custom elements to encapsulate repeating patterns, which can provide a framework-like organization while staying standard ([thenewstack.io](https://thenewstack.io/web-components-are-the-comeback-nobody-saw-coming/#:~:text=For%20years%2C%20web%20components%20have,supported%20and%20almost%20entirely%20ignored)). Documentation becomes critical – where a framework might enforce file organization or provide CLI tooling, an HTML-first project should have a well-documented architecture (explaining how a new interactive widget should be built with progressive enhancement, for example). On the plus side, not using a large framework means there is no constant churn of framework versions or breaking changes to manage. The app’s core (HTML, CSS, light JS) is based on long-lived standards. Developers have reported that this leads to a simpler development experience and easier onboarding, as anyone comfortable with web basics can understand the project ([hotwired.dev](https://hotwired.dev/#:~:text=using%20much%20JavaScript%20by%20sending,speed%20or%20responsiveness%20associated%20with)).
  - Implications: Maintaining an HTML-first codebase might require more discipline, since there's less imposed structure. Teams might fill that gap with things like server-side MVC frameworks or static analyzers for consistent code style. Over time, if the project grows extremely complex, they might selectively introduce a bit more client-side structure (for example, using a small reactive library for one complex section). But importantly, because the bulk of the app is standard HTML/CSS, the risk of tech lock-in is low – you could gradually refactor or even integrate parts with a framework if truly needed, without having to rewrite everything. Security-wise, fewer moving parts can mean fewer vulnerabilities, though developers must be careful with manual DOM operations (to avoid XSS, always sanitize or use safe APIs when injecting HTML). Regular code reviews and refactoring are advisable to keep the codebase clean. In sum, a well-run HTML-first project can be just as maintainable as a framework-based one, provided the team actively manages consistency and quality.
