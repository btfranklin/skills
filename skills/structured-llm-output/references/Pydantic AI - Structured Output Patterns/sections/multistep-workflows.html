Summary

For complex extraction tasks (long documents or many fields), a single prompt might not suffice. This section explores breaking the task into multiple steps – for example, processing a document in sections or using one LLM pass to verify another’s output. It examines strategies like chunking inputs, using one model to check another’s results, iterative refinement of answers, and integrating human review for critical data points.

Insights

Chunking content and preserving structure enhances extraction

Evidence
Dividing a large input (like a long document) into logical sections can lead to better accuracy. Microsoft’s approach with Document Intelligence involves splitting documents into sections and subsections (using semantic layout) before feeding to the LLM (techcommunity.microsoft.com). By doing so, the model can focus on one part at a time with relevant context, and the relationships between sections (headings, paragraphs, tables) are maintained. This contextual chunking prevents the model from getting overwhelmed and helps it extract data more precisely from each segment.
Implications
Processing text in smaller, structured chunks reduces the chance of the model missing details or mixing up information from different parts. It also aligns with token limits – each chunk stays within size bounds. The trade-off is that chunking requires post-processing to merge results and ensure nothing was duplicated or skipped, but the overall reliability of extraction is higher than a single-pass sweep of a huge text.

Dual-model validation setup can guarantee higher accuracy

Evidence
For critical extractions, one pattern is to use a second model or process to validate the first model’s output. In a dual-LLM pipeline, the first LLM extracts data into JSON, and then a second call (or different model) cross-checks those values against the source document or an alternate extractor (techcommunity.microsoft.com). Any discrepancies trigger flags. Microsoft’s implementation of this sends the conflicting results to a human interface for review (techcommunity.microsoft.com), acknowledging that even with automation, a human-in-the-loop may be needed for edge cases. This approach recognizes that while one LLM might err, a combination of two (and a human for final arbitration) can reach near 100% accuracy (techcommunity.microsoft.com).
Implications
By incorporating a validation stage, we catch mistakes that a single-pass system might silently overlook. It’s essentially redundancy for quality assurance. The cost is doubled AI usage and added complexity, but for domains like finance or healthcare, the improved precision is often worth it. Over time, if the LLMs prove consistently accurate, the human involvement can be dialed back – but having that safety net initially builds trust in the system.

Orchestrating multi-step chains brings modularity and control

Evidence
Frameworks like LangChain allow developers to compose multi-step workflows (prompt → model → output parser → another model, etc.) in a clear, testable manner (blog.thegenairevolution.com). For example, one can define a chain that first calls an LLM to extract a list of entities, then calls another chain for each entity to get details, and finally validates all outputs. By using such pipelines, it’s easier to swap models or adjust prompts for one step without affecting others (blog.thegenairevolution.com). Another best practice is running the model at temperature 0 when consistency is paramount – this makes the output deterministic for the same input (blog.thegenairevolution.com), which is crucial for testing and debugging multi-step logic.
Implications
Modular pipelines increase maintainability of complex extraction systems. If one part of the extraction fails or changes (say we replace GPT-4 with an open model for cost reasons), a well-structured chain containing that step can be updated in isolation. Deterministic behavior (no randomness) in non-creative tasks means if something worked once, it will continue to work, which is exactly what you want in a production data pipeline.
