Summary

Multiple approaches have emerged to get structured JSON-like outputs from LLMs. This section compares using Pydantic-based validation versus model-native features (like OpenAI’s function calling with JSON schemas) and purpose-built libraries (like Instructor). It examines their reliability guarantees, ease of use, and compatibility across different model providers.

Key Terms

  • PydanticAI
  • OpenAI function calling
  • JSON schema
  • Instructor library
  • tool integration
  • provider-agnostic

Guiding Questions

  • What are the differences between externally validating outputs vs. having the model itself constrained by a schema?
  • How do OpenAI’s structured output features compare to open-source libraries like Instructor or LangChain output parsers?
  • What failure modes remain (e.g., hallucinated fields) under each approach, and how portable are these methods to other models?

Insights

Schema validation can be layered on any LLM via PydanticAI

Evidence
Even without native support, we can force structured outputs by prompting and then validating. The PydanticAI framework, for example, wraps an LLM call with a Pydantic model check – you define exactly what the output should contain and it ensures the model sticks to that format (codecut.ai). This works across virtually all providers, from OpenAI to open-source models, since it doesn’t rely on proprietary features but on post-processing the model’s text.
Implications
This approach is very flexible: it’s model-agnostic and can leverage any LLM. However, because the LLM isn’t guaranteed to comply, it may require multiple attempts or clever prompting to get a valid output. The burden of correctness lies partly on the application to catch and correct errors, rather than the model always being right on the first try.

OpenAI’s native structured output achieves high reliability

Evidence
OpenAI introduced a mode where models like GPT-4 can be constrained to output a JSON object fitting a given schema. In internal evaluations, the structured-output fine-tuned model achieved a 100% adherence rate to complex schemas (openai.com), compared to less than 40% for the regular GPT-4 model. This is done by the model architecture itself honoring the schema (using function calling with strict=true or similar), so the JSON never has missing keys or wrong types as long as the request is within allowed policy.
Implications
When using OpenAI’s structured output feature, developers get a guarantee that the format will be correct, drastically reducing the need for retries or fixes. The trade-off is vendor lock-in to OpenAI’s ecosystem for this guarantee – and it’s only available on models that have been tuned for it. Also, if the model refuses (due to content policy) or if the schema itself doesn’t cover a scenario, the developer must handle those cases (like receiving a special ‘refusal’ response) nonetheless.

Instructor library provides a unified, type-safe interface

Evidence
The Instructor library (by 567 Labs) wraps around providers like OpenAI to yield structured data according to Pydantic models (medium.com). With Instructor, developers define output schemas as Pydantic classes, and the library handles prompting the LLM and validating the response. It’s designed to be multi-platform: one can switch the backend model (OpenAI, Anthropic, etc.) while keeping the same schema enforcement. Under the hood, it uses the model’s capabilities (like OpenAI’s JSON mode when available) and falls back to validation and re-prompting when needed.
Implications
Using a library like Instructor can speed up development since it abstracts the boilerplate of writing prompts and retry loops for structure. It also means less manual handling of each provider’s quirks. However, it’s an additional dependency and could introduce overhead in how requests are made. It’s essentially layering Pydantic validation logic on top of model APIs – beneficial for consistency, but developers should be aware of how errors are handled internally (to avoid black-box scenarios).

Choosing the right approach depends on context and constraints

Evidence
Each method has trade-offs. External validation (Pydantic in the app) is versatile but may require multiple attempts for complex outputs. Native structured output (OpenAI) is extremely reliable format-wise but ties you to specific models and schemas. Library frameworks strike a middle ground by automating enforcement across providers. In practice, simpler extraction tasks might be solved with direct Pydantic parsing, whereas more complex or critical workflows benefit from robust schema enforcement and possibly a combination of techniques (codecut.ai).
Implications
Engineers should evaluate the complexity of the extraction task and the acceptable error rate. For example, if using open-source models or needing custom validation, sticking with Pydantic + custom logic makes sense. If operating mostly in OpenAI’s ecosystem and needing absolute format guarantees, leveraging function calling with strict schemas will save time. Often, hybrid strategies emerge – e.g., use structured outputs when possible, but still validate with Pydantic to double-check or to post-process into Python objects.
